# Niche Score v1

## Что это и чем не является

Niche Score — **инструмент сравнения ниш между собой**, а не измерение
абсолютной привлекательности. Число 72 не означает «ниша хороша на 72%». Оно
означает «на текущем датасете эта ниша выглядит заметно лучше остальных по
взвешенной сумме компонентов».

Score обязан читаться вместе с разбивкой по компонентам. Итоговая цифра нужна
для сортировки, объяснение — в компонентах.

## Формула

```
score = Σ (weight_i × component_i) / Σ weight_i     по ДОСТУПНЫМ компонентам
```

Каждый компонент приведён к шкале 0–100 и ориентирован так, что **больше —
всегда лучше**. Факторы, плохие по своей природе (конкуренция, стоимость
производства, риск монетизации), инвертируются *до* взвешивания. Поэтому
формула — обычное взвешенное среднее, без жонглирования знаками.

## Компоненты

| Компонент | Источник | Показатель | Вес |
|---|---|---|---:|
| `audience_value` | данные | медианный CPV | 0.14 |
| `ad_budget_level` | данные | медианная стоимость размещения | 0.10 |
| `engagement` | данные | медианный ERR | 0.13 |
| `reach_efficiency` | данные | медиана просмотры/подписчики | 0.10 |
| `market_size` | данные | число каналов в нише | 0.08 |
| `low_competition` | данные | инвертированная доля топ-N по подписчикам | 0.13 |
| `growth_potential` | данные | медианный прирост подписчиков между датами | 0.07 |
| `content_scalability` | оценка | насколько легко делать контент потоком | 0.09 |
| `low_production_cost` | оценка | инвертированная стоимость производства | 0.06 |
| `originality_potential` | оценка | простор для оригинального материала | 0.04 |
| `brand_safety` | оценка | дружелюбность темы к рекламодателям | 0.03 |
| `low_monetization_risk` | оценка | инвертированный риск ограничений площадок | 0.03 |

Данные дают 0.75 веса, субъективные оценки — 0.25. Веса задаются в
`config/niche_score.yaml` и должны суммироваться в 1.0 (проверяется при
загрузке).

## Нормализация: перцентильный ранг

Компоненты из данных приводятся к 0–100 **перцентильным рангом** среди других
ниш того же прогона:

```
percentile = (сколько ниш ниже + 0.5 × сколько равны) / всего × 100
```

Почему не min-max: min-max масштабирование чувствительно к выбросам — одна
аномальная ниша сожмёт все остальные в узкую полосу. Перцентильный ранг к
этому невосприимчив по построению. Это та же логика, по которой внутри ниши
берутся медиана и квартили, а не среднее.

Следствие, о котором нужно помнить: **перцентиль относителен**. Ниша с рангом
88 не «хороша сама по себе» — она лучше 88% ниш в этом датасете. При 4 нишах
шкала грубая, поэтому отчёт помечает такое ранжирование как низкодостоверное.

## Недоступные компоненты: перенормировка, а не выдумывание

Если компонент нельзя посчитать (в выгрузке нет CPV; нет второй даты снимка для
роста), он **исключается** для этой ниши, а веса оставшихся пропорционально
перенормируются. Пропуск никогда не заполняется нулём, средним или любым другим
придуманным значением.

Отдельный случай: доля топ-N считается только при числе каналов **больше** N.
В нише из трёх каналов топ-3 — это вся ниша, и доля равна 100% по построению.
Показывать это как «максимальная конкуренция» значило бы штрафовать нишу за
размер нашей выборки, а не за состояние рынка, поэтому компонент считается
недоступным.

## Субъективные оценки

Пять компонентов — это суждения, а не измерения. Они задаются вручную по шкале
0–100:

```
0-20    очень плохо / очень сложно
20-40   плохо / сложно
40-60   средне
60-80   хорошо / легко
80-100  отлично / тривиально
```

Пока для ниши нет override, используется нейтральное значение 50 — то есть
субъективные компоненты **не различают ниши** и не могут незаметно повлиять на
рейтинг. Отчёты и CLI явно сообщают, сколько ниш ещё на значениях по умолчанию.

Задать оценки для ниши (slug виден в `show-top-niches` и в CSV):

```yaml
manual_overrides:
  ai-i-tehnologii:
    content_scalability: 85
    production_cost: 35
    brand_safety: 90
```

## Пороги

| Параметр | Значение | Смысл |
|---|---:|---|
| `min_channels_for_scoring` | 3 | Ниши с меньшим числом каналов не ранжируются: медиана по одному-двум каналам описывает эти каналы, а не нишу |
| `top_channels_for_concentration` | 3 | Сколько каналов считается «верхушкой» ниши |
| `low_confidence_niche_count` | 5 | Ниже этого числа ранжирование помечается как низкодостоверное |

Ниши, не прошедшие порог, не выбрасываются: они сохраняются с флагом
`insufficient_data` и перечисляются в отчёте. Они также **не участвуют** в
расчёте перцентилей, чтобы не искажать шкалу для остальных.

## Версионирование

`score_version` (`niche_score_v1`) хранится в каждой строке `niche_scores`.
Прогоны append-only: новый запуск `analyze-niches` создаёт новую строку в
`niche_score_runs` и новые строки оценок, старые не изменяются.

Каждый прогон сохраняет использованные веса, пороги и описание датасета, а
каждая строка — полную разбивку по компонентам. Поэтому прошлый рейтинг можно
объяснить и воспроизвести после изменения формулы.

Меняя формулу, поднимайте версию: `niche_score_v2` — новый модуль расчёта и
новое значение `score_version`. Старые строки не пересчитываются задним числом.

## Чего формула не делает

* Не учитывает число рекламодателей — такого поля нет в выгрузках, и оно не
  выдумывается. Если колонка появится, компонент можно добавить в v2.
* Не прогнозирует доход канала.
* Не заменяет ручной анализ лидеров ниши (это PHASE 3).
* Не даёт устойчивого результата на 3–4 нишах: сначала нужны данные пошире.
