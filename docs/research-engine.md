# Autonomous Research Engine

Собирает публикации из разрешённых источников, схлопывает их в информационные
события и оценивает пригодность для контента. Fact check, генерация и
публикация — следующие фазы; этот модуль только доводит поток до состояния
«вот темы, вот почему они выбраны».

## Границы: что делаем мы, а что Claude Routines

Runtime целиком живёт внутри `yan-channel-factory`, потому что Claude Routine
выполняется в облаке Anthropic и **не имеет доступа** к локальной PostgreSQL.
Ставить его в конвейер, где нужен гарантированный контракт данных, нельзя.

| Задача | Где |
|---|---|
| Опрос источников, дедуп, скоринг | yan-channel-factory |
| AI-скаутинг трендов | yan-channel-factory, через `LLMSearchProvider` |
| Weekly source discovery, weekly editorial audit, monthly market review | Claude Routines, результат — отчёт в репозиторий |

Routine никогда не пишет в базу и не является source of truth.

## Источники

Whitelist в `config/research_sources.yaml`. Каждый источник обязан иметь
`reason` — зачем он нужен. Источник «для количества» не добавляется.

| Provider | Что читает |
|---|---|
| `RSS` | Любой валидный RSS/Atom |
| `GITHUB_RELEASES` | `GET /repos/{repo}/releases` официального API |
| `OFFICIAL_BLOG` | Листинг официальной страницы из whitelist |
| `LLM_SEARCH` | Anthropic API + серверный tool `web_search` |

`OfficialBlogProvider` намеренно примитивен: берёт ссылки из листинга нужного
раздела и их текст. Он не ходит по статьям, не исполняет JavaScript и не имеет
правил под конкретные сайты. Если важному источнику этого мало — он получает
**свой** адаптер; делать общий парсер умнее запрещено.

Чего мы не делаем ни при каких условиях: обход авторизации, CAPTCHA, anti-bot,
private API, извлечение cookie. Источник, отвечающий 403 на автоматические
запросы, отключается с указанием причины — так уже отключены `openai-news`
и `perplexity`.

## Идентичность и обновления

Три разных вопроса требуют трёх разных ключей, и их смешение — классический
источник и пропущенных дублей, и потерянных обновлений.

| Вопрос | Ключ |
|---|---|
| Тот же документ у того же источника? | `UNIQUE(research_source_id, external_id)` |
| Тот же адрес? | `canonical_url` / `url_hash` (индекс, **не** уникальный) |
| Контент по адресу изменился? | `content_fingerprint` |

`external_id` — это guid фида, id релиза или, если провайдер не даёт ничего
лучше, канонический URL. Поэтому естественный ключ существует всегда.

Канонизация URL убирает `utm_*` и трекинговые параметры, `www.`, порт по
умолчанию, фрагмент и хвостовой слэш, а оставшиеся параметры сортирует.

Изменившийся `content_fingerprint` при том же `external_id` — это **обновление**,
а не новый элемент: строка одна, `revision` растёт, ставится
`content_changed_at`, а кластер помечается на пересчёт. Полные тексты чужих
страниц не хранятся — только `summary` и ограниченный `content_excerpt`.

## Дедупликация

Четыре слоя, от дешёвого к дорогому; каждый следующий применяется только к
тому, что не решил предыдущий.

1. **Canonical URL** — один адрес, один документ.
2. **Content fingerprint** — тот же текст в другом месте.
3. **Entity + окно времени** — `vendor:product:version` в пределах 72 часов.
4. **SimHash** — почти совпадающие формулировки, расстояние Хэмминга ≤ 6.

Векторных эмбеддингов нет намеренно: они потребовали бы отдельного модельного
стека ради задачи, с которой эти слои справляются на наших объёмах.

Три правила, которые появились не из теории, а из реальных данных:

* **Явный идентификатор побеждает нечёткое сходство.** Подряд идущие релизы
  делят почти весь текст changelog: десять релизов n8n схлопнулись в один
  кластер, пока несовпадение версии не начало ветировать слой SimHash и
  fingerprint.
* **Короткий текст не сравнивается по SimHash.** Заголовок «stable» из двух
  токенов даёт шум, а не сходство.
* **Fallback-ключ кластера обязан быть уникальным.** Пока он строился из
  SimHash, одинаковые тексты снова сливались уже поиском по ключу — сразу
  после того, как матчер их развёл.

Подсказки от провайдера (`tag_name`, `repo`) сильнее выводов из заголовка:
релиз знает свой тег, даже когда его заголовок — просто «stable».

Тип события нормализуется: `RELEASE`, `UPDATE`, `NEW_TOOL` и нераспознанное
попадают в общую корзину «announcement», потому что одно издание «представляет»
то, что другое называет «now available». Отдельную идентичность сохраняют
только `GUIDE`, `RESEARCH` и `INCIDENT`.

## Модель доверия

```
OFFICIAL            100  сайт, блог, changelog или репозиторий вендора
PRIMARY              85  первоисточник (официальный анонс, статья)
REPUTABLE_SECONDARY  60  издание с редакцией
AGGREGATOR           35  агрегаторы и репосты
UNKNOWN              15  нерезолвленный домен
```

Результаты `LLM_SEARCH` всегда начинают с `UNKNOWN`: находка не может сама себе
выдать авторитет. Компонент `authority` берётся прямо отсюда.

## Topic Score v1

```
score = Σ (weight_i × component_i) / Σ weight_i    по ДОСТУПНЫМ компонентам
```

| Компонент | Тип | Вес |
|---|---|---:|
| `relevance` | LLM | 0.22 |
| `practical_value` | LLM | 0.20 |
| `novelty` | детерминированный | 0.15 |
| `authority` | детерминированный | 0.13 |
| `timeliness` | детерминированный | 0.12 |
| `audience_fit` | LLM | 0.10 |
| `content_potential` | LLM | 0.08 |

Недоступный компонент исключается с перенормировкой весов — тот же механизм,
что в Niche Score.

### Три уровня доступности

У `relevance` и `practical_value` есть **бесплатный детерминированный
фолбэк** — лексикон (`config/topic_lexicon.yaml`). Приоритет такой:

```
суждение LLM  >  лексикон  >  компонент недоступен
```

| Что настроено | Покрытие веса | Качество отбора |
|---|---:|---|
| Ничего | 0.40 | Отбора фактически нет |
| Лексикон (по умолчанию) | 0.82 | Рабочий |
| Лексикон + LLM | 1.00 | Лучший |

Измерено на 423 реальных кластерах:

| | Без лексикона | С лексиконом |
|---|---:|---:|
| SELECTED | 240 | **21** |
| BACKLOG | 183 | 384 |
| FILTERED | 0 | 18 |

Без лексикона в топе стояли «Visual Studio Code 1.137» и «5 лучших приложений
для дневника» с одинаковыми 100 — оценка отвечала лишь на вопрос «свежее ли и
от официального ли источника», а в кураторском whitelist это верно почти для
всего. С лексиконом топ занимают «ChatGPT Scheduled Tasks: how to use them»,
«How to train ChatGPT to write like you», «What are Gemini Gems?» — то есть
ровно ниша, а рассуждения и корпоративные новости уходят в FILTERED.

### Лексикон

Аддитивная схема от нейтральной базы: положительные термины ниши (`промпт`,
`workflow`, `excel`, `how to`) складываются, отрицательные (`funding`, `ipo`,
`партнёрств`, `назначен`) вычитаются, результат зажимается в 0–100. Каждый
термин считается один раз.

Это **эвристика, а не суждение**, и она себя объявляет: в разбивке компонента
видно, какие слова сработали — например `+chatgpt, prompt, how to`. Настройка
делается правкой YAML, без кода.

Практическая ценность читается в основном из заголовка (обещание действия —
самый сильный сигнал, доступный без модели), тело учитывается с половинным
весом, плюс бонус за тип события и наличие версии.

### Судьба кластера

```
score ≥ 70  → SELECTED
45 … 69     → BACKLOG
< 45        → FILTERED
```

Ни одно из этих решений не окончательно. Кластер, получивший новые источники,
помечается `needs_rescore` и оценивается заново, поэтому `FILTERED` — это
парковка, а не отказ.

`REJECTED` ставится **только** по явной причине: нерелевантно, спам, опасная
тема, подтверждённый мусор, ручное исключение. Низкая оценка такой причиной не
является.

## Контроль расходов

Провайдер выбирается сам, и **бесплатная ёмкость имеет приоритет над платной**:

| Условие | Кто судит | Стоимость |
|---|---|---|
| Задан `GEMINI_API_KEY` | Gemini free tier | $0, лимит — 1000 запросов/сутки |
| Задан только `ANTHROPIC_API_KEY` | Anthropic API | ~$2.75/мес на наших объёмах |
| Ключей нет | Лексикон | $0 |

У бесплатного тарифа ограничивающий ресурс — не деньги, а суточная квота
запросов, поэтому она и ограничивается, причём по той же таблице
`ai_generations`, что и платный путь. Оговорка, которую надо знать: на
бесплатном тарифе Google может использовать промпты и ответы для улучшения
своих продуктов — мы отправляем туда только публичные заголовки и аннотации.

Роутинг моделей Anthropic — политика, а не оптимизация:

| Задача | Модель |
|---|---|
| Извлечение, классификация, скоринг, арбитраж дублей | `claude-haiku-4-5` |
| Синтез, разбор противоречий | `claude-sonnet-5` |
| Runtime | Opus не используется |

Каждый вызов пишется в `ai_generations` с токенами, стоимостью и задержкой.
Лимиты `daily_cost_limit_usd` и `monthly_cost_limit_usd` проверяются **до**
вызова и считаются суммой по той же таблице — то есть цифра лимита и цифра
расхода не могут разойтись. При достижении лимита новые LLM-вызовы
блокируются, а сбор источников продолжается.

Неизвестная модель в прайс-листе — ошибка, а не нулевая стоимость: иначе смена
роутинга молча обнулила бы смысл лимитов.

Структурированный вывод получается через инструмент со `strict: true`, а не
парсингом свободного JSON: некорректный ответ модели не может попасть в базу.

## Наблюдаемость

Каждый запуск джоба пишет строку в `pipeline_runs` со счётчиками и
длительностью. Каждая оценка кластера — строку в `topic_scores` с полной
разбивкой по компонентам, включая недоступные. Команда `show-cluster` отвечает
на вопрос «почему эта тема выбрана» без повторного расчёта.

## Команды

```bash
uv run python -m channel_factory.cli research-sync-sources
uv run python -m channel_factory.cli research-poll --force
uv run python -m channel_factory.cli research-cluster
uv run python -m channel_factory.cli score-topics --no-llm
uv run python -m channel_factory.cli show-clusters --status SELECTED
uv run python -m channel_factory.cli show-cluster <uuid>
uv run python -m channel_factory.cli research-status
uv run python -m channel_factory.cli ai-cost
uv run python -m channel_factory.cli research-report
```

Демон-планировщик в эту фазу не входит: джобы запускаются вручную. APScheduler
3.x появится отдельной фазой (4.0 официально помечен как не готовый к
production), и отвечать он будет только за тайминг — состояние работ остаётся
в PostgreSQL.
